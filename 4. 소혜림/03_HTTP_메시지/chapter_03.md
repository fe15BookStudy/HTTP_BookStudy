# HTTP 메시지

## 메시지의 흐름

- HTTP 메시지는 **클라이언트, 서버, 프락시** 사이를 오가는 데이터 블록.
- 구조: **텍스트 기반의 메타 정보(헤더)** + **선택적 본문(데이터)**
- 방향 개념
  - 인바운드: 원 서버로 향하는 메시지
  - 아웃바운드: 원 서버에서 사용자 에이전트로 돌아오는 메시지
  - 업스트림: 메시지를 보낸 쪽
  - 다운스트림: 메시지를 받은 쪽
- **항상 다운스트림**으로 흐름 (요청·응답 모두 동일).

---

## 메시지의 구성 요소

1. **시작줄 (Start Line)** – 메시지의 성격 설명
2. **헤더 블록 (Headers)** – 속성 정보 전달
3. **본문 (Body)** – 실제 데이터, 없을 수도 있음

---

## 메시지 문법

### 요청 메시지

<메서드> <요청 URL> <버전> CRLF
<헤더> CRLF
CRLF
<엔터티 본문>

### 응답 메시지

<버전> <상태 코드> <사유 구절> CRLF
<헤더> CRLF
CRLF
<엔터티 본문>

- 마지막 CRLF가 빠져도 동작하도록 구현체들이 허용해야 한다.

---

## 시작줄

### 요청줄 (Request Line)

- 포함 요소: 메서드 + 요청 URL + HTTP 버전
- 필드는 공백으로 구분
- HTTP/1.0 이전에는 버전이 없어도 됨
- 예: `GET /index.html HTTP/1.1`

### 응답줄 (Status Line)

- 포함 요소: HTTP 버전 + 상태 코드 + 사유 구절
- 필드는 공백으로 구분
- HTTP/1.0 이전에는 응답줄이 없어도 됨
- 예: `HTTP/1.1 200 OK`

---

## 메서드 (Method)

- 요청 메시지의 시작줄 첫 요소.
- 서버가 해야 할 동작을 지시.

| 메서드  | 설명                           | 본문 |
| ------- | ------------------------------ | ---- |
| GET     | 서버에서 리소스 가져오기       | X    |
| HEAD    | 리소스의 헤더만 가져오기       | X    |
| POST    | 서버가 처리해야 할 데이터 전송 | O    |
| PUT     | 본문 데이터를 서버에 저장      | O    |
| TRACE   | 메시지 경로 추적               | X    |
| OPTIONS | 서버가 지원하는 메서드 확인    | X    |
| DELETE  | 서버에서 리소스 삭제           | X    |

- 모든 서버가 다 지원하는 것은 아님.
- HTTP는 확장 가능하므로, 새 메서드를 추가할 수도 있다.

---

## 상태 코드 (Status Code)

- 응답 시작줄에 포함, 요청 처리 결과를 숫자로 전달.
- **숫자 코드**는 기계가 처리, **사유 구절**은 사람이 읽도록 제공.

### 분류

- 1xx: 정보 (예: 100 Continue)
- 2xx: 성공 (예: 200 OK)
- 3xx: 리다이렉션 (예: 301 Moved Permanently)
- 4xx: 클라이언트 에러 (예: 404 Not Found)
- 5xx: 서버 에러 (예: 500 Internal Server Error)

- 확장 상태 코드: 명세에 없더라도 범주에 따라 해석해야 함.
  - 예: `515` → 5xx 범주이므로 서버 에러

---

## 사유 구절 (Reason Phrase)

- 상태 코드 뒤에 붙는 짧은 설명 텍스트.
- 예: `200 OK`, `404 Not Found`
- 표현은 자유롭지만 의미는 숫자 코드로만 결정된다.
  - `200 OK`와 `200 NOT OK` → 동일하게 성공 처리

---

## 버전 번호 (HTTP Version)

- 형식: `HTTP/<메이저>.<마이너>`
- 애플리케이션 간 지원 프로토콜 버전 공유.
- 숫자는 분리해 비교 (분수처럼 취급하지 않음).
  - 예: `HTTP/2.22` > `HTTP/2.3`

---

## 헤더 (Header)

- 요청/응답에 추가 정보 제공.
- 문법: `이름: 값 CRLF`
- 반드시 CRLF로 끝나며, 헤더 목록 끝도 빈 줄(CRLF)로 표시.

### 분류

- 일반 헤더 – 요청·응답 모두 가능
- 요청 헤더 – 요청에 대한 부가 정보
- 응답 헤더 – 응답에 대한 부가 정보
- 엔터티 헤더 – 본문 크기, 콘텐츠 등 설명
- 확장 헤더 – 명세에 없는 사용자 정의 헤더

### 예시

- `Date: Tue, 3 Oct 1997 02:16:03 GMT` – 응답 생성 시각
- `Content-Length: 15040` – 본문 크기
- `Content-Type: image/gif` – 본문 데이터 타입
- `Accept: image/gif, image/jpeg, text/html` – 클라이언트가 허용하는 타입

### 긴 헤더 줄

- 여러 줄로 나눌 수 있으며, 다음 줄은 스페이스나 탭으로 시작해야 한다.

---

## 엔터티 본문 (Entity Body)

- 메시지의 **화물(payload)**
- 선택적이며 텍스트/이진 데이터 모두 포함 가능
- 예: 이미지, 비디오, HTML, 소프트웨어, 결제 정보, 이메일 등
