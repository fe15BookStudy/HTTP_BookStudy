# HTTP 메시지

## 메시지의 흐름

- HTTP 메시지는 **클라이언트, 서버, 프락시** 사이를 오가는 데이터 블록.
- 구조: **텍스트 기반의 메타 정보(헤더)** + **선택적 본문(데이터)**
- 방향 개념
  - 인바운드: 원 서버로 향하는 메시지
  - 아웃바운드: 원 서버에서 사용자 에이전트로 돌아오는 메시지
  - 업스트림: 메시지를 보낸 쪽
  - 다운스트림: 메시지를 받은 쪽
- **항상 다운스트림**으로 흐름 (요청·응답 모두 동일).

---

## 메시지의 구성 요소

1. **시작줄 (Start Line)** – 메시지의 성격 설명
2. **헤더 블록 (Headers)** – 속성 정보 전달
3. **본문 (Body)** – 실제 데이터, 없을 수도 있음

---

## 메시지 문법

### 요청 메시지

<메서드> <요청 URL> <버전> CRLF
<헤더> CRLF
CRLF
<엔터티 본문>

### 응답 메시지

<버전> <상태 코드> <사유 구절> CRLF
<헤더> CRLF
CRLF
<엔터티 본문>

- 마지막 CRLF가 빠져도 동작하도록 구현체들이 허용해야 한다.

---

## 시작줄

### 요청줄 (Request Line)

- 포함 요소: 메서드 + 요청 URL + HTTP 버전
- 필드는 공백으로 구분
- HTTP/1.0 이전에는 버전이 없어도 됨
- 예: `GET /index.html HTTP/1.1`

### 응답줄 (Status Line)

- 포함 요소: HTTP 버전 + 상태 코드 + 사유 구절
- 필드는 공백으로 구분
- HTTP/1.0 이전에는 응답줄이 없어도 됨
- 예: `HTTP/1.1 200 OK`

---

## 메서드 (Method)

- 요청 메시지의 시작줄 첫 요소.
- 서버가 해야 할 동작을 지시.

| 메서드  | 설명                           | 본문 |
| ------- | ------------------------------ | ---- |
| GET     | 서버에서 리소스 가져오기       | X    |
| HEAD    | 리소스의 헤더만 가져오기       | X    |
| POST    | 서버가 처리해야 할 데이터 전송 | O    |
| PUT     | 본문 데이터를 서버에 저장      | O    |
| TRACE   | 메시지 경로 추적               | X    |
| OPTIONS | 서버가 지원하는 메서드 확인    | X    |
| DELETE  | 서버에서 리소스 삭제           | X    |

- 모든 서버가 다 지원하는 것은 아님.
- HTTP는 확장 가능하므로, 새 메서드를 추가할 수도 있다.

---

## 상태 코드 (Status Code)

- 응답 시작줄에 포함, 요청 처리 결과를 숫자로 전달.
- **숫자 코드**는 기계가 처리, **사유 구절**은 사람이 읽도록 제공.

### 분류

- 1xx: 정보 (예: 100 Continue)
- 2xx: 성공 (예: 200 OK)
- 3xx: 리다이렉션 (예: 301 Moved Permanently)
- 4xx: 클라이언트 에러 (예: 404 Not Found)
- 5xx: 서버 에러 (예: 500 Internal Server Error)

- 확장 상태 코드: 명세에 없더라도 범주에 따라 해석해야 함.
  - 예: `515` → 5xx 범주이므로 서버 에러

---

## 사유 구절 (Reason Phrase)

- 상태 코드 뒤에 붙는 짧은 설명 텍스트.
- 예: `200 OK`, `404 Not Found`
- 표현은 자유롭지만 의미는 숫자 코드로만 결정된다.
  - `200 OK`와 `200 NOT OK` → 동일하게 성공 처리

---

## 버전 번호 (HTTP Version)

- 형식: `HTTP/<메이저>.<마이너>`
- 애플리케이션 간 지원 프로토콜 버전 공유.
- 숫자는 분리해 비교 (분수처럼 취급하지 않음).
  - 예: `HTTP/2.22` > `HTTP/2.3`

---

## 헤더 (Header)

- 요청/응답에 추가 정보 제공.
- 문법: `이름: 값 CRLF`
- 반드시 CRLF로 끝나며, 헤더 목록 끝도 빈 줄(CRLF)로 표시.

### 분류

- 일반 헤더 – 요청·응답 모두 가능
- 요청 헤더 – 요청에 대한 부가 정보
- 응답 헤더 – 응답에 대한 부가 정보
- 엔터티 헤더 – 본문 크기, 콘텐츠 등 설명
- 확장 헤더 – 명세에 없는 사용자 정의 헤더

### 예시

- `Date: Tue, 3 Oct 1997 02:16:03 GMT` – 응답 생성 시각
- `Content-Length: 15040` – 본문 크기
- `Content-Type: image/gif` – 본문 데이터 타입
- `Accept: image/gif, image/jpeg, text/html` – 클라이언트가 허용하는 타입

### 긴 헤더 줄

- 여러 줄로 나눌 수 있으며, 다음 줄은 스페이스나 탭으로 시작해야 한다.

---

## 엔터티 본문 (Entity Body)

- 메시지의 **화물(payload)**
- 선택적이며 텍스트/이진 데이터 모두 포함 가능
- 예: 이미지, 비디오, HTML, 소프트웨어, 결제 정보, 이메일 등

---

## 메서드

- 모든 서버가 모든 메서드를 구현하지는 않는다.
- HTTP/1.1 호환을 위해서는 **GET**과 **HEAD**만 구현해도 충분하다.
- **PUT**, **DELETE** 같은 메서드는 보안상의 이유로 제한적으로 사용되며, 서버 설정에 따라 달라진다.

---

### 안전한 메서드

- **GET**, **HEAD**는 안전한 메서드로 분류된다.
- 안전 = 요청이 서버에 **영향(작용)**을 주지 않아야 함.
- 하지만 실제로는 부작용이 생길 수도 있다.
- 이 구분의 목적은 **안전하지 않은 메서드(예: POST)** 사용 시 사용자에게 경고를 줄 수 있도록 하기 위함이다.

---

### GET

- 가장 흔히 쓰이는 메서드.
- 서버에 리소스를 요청할 때 사용.
- HTTP/1.1에서는 반드시 구현해야 함.

---

### HEAD

- GET과 동일하게 동작하지만 **본문 없이 헤더만 반환**.
- 활용:
  - 리소스 메타데이터 확인 (타임스탬프, 크기 등)
  - 상태 코드로 리소스 존재 여부 확인
  - 리소스 변경 여부 검사
- 반환되는 헤더는 GET과 동일해야 함.
- HTTP/1.1 준수를 위해 반드시 구현해야 함.

---

### PUT

- 서버에 리소스를 저장하거나 교체.
- 요청 URL이 새 리소스면 생성, 기존 리소스면 교체.
- 사용 예: 게시 시스템에서 문서를 직접 업로드.
- 보안상, 대부분 서버는 PUT 실행 전에 인증을 요구한다.

---

### POST

- 서버에 **입력 데이터 전송**을 위해 설계됨.
- HTML 폼 데이터 전송에 주로 사용.
- 클라이언트가 입력한 데이터를 서버가 수집해 다른 프로그램(예: 게이트웨이)으로 전달해 처리한다.

---

### TRACE

- 요청이 방화벽, 프락시, 게이트웨이 등을 거치며 수정될 수 있음.
- TRACE는 클라이언트가 최종적으로 서버에 도달한 요청이 어떻게 보이는지 확인할 수 있게 한다.
- 동작:
  - 서버가 받은 요청 메시지를 그대로 본문에 담아 응답으로 돌려줌 (**루프백 진단**).
- 용도:
  - 요청/응답 경로를 따라가며 메시지가 변형되었는지 확인.
  - 중간 애플리케이션(프락시 등)이 요청에 미친 영향을 확인.
- 특징:
  - 주로 **진단 목적**으로 사용됨.
  - 엔터티 본문은 보낼 수 없음.
  - 응답 본문에는 서버가 받은 요청이 그대로 들어있다.

---

## 상태 코드

HTTP 상태 코드는 크게 다섯 가지로 나뉜다.  
클라이언트가 트랜잭션 결과를 쉽게 이해할 수 있도록 돕는다.

---

### 100–199: 정보성 상태 코드

- HTTP/1.1에서 새로 도입됨.
- 비교적 새로운 개념이라 사용 가치에 논란이 있음.

#### 주요 코드

- **100 Continue**

  - 요청 일부가 받아들여졌으며, 클라이언트는 나머지를 계속 전송해야 함.
  - 서버는 이 코드를 보낸 후 반드시 최종 응답을 돌려줘야 한다.
  - 의도: 클라이언트가 큰 본문을 보내기 전에 서버가 수락 여부를 확인 → 전송 최적화.
  - 하지만 혼란을 일으키는 경우가 많다.

- **101 Switching Protocols**
  - 클라이언트가 `Upgrade` 헤더로 제안한 프로토콜 중 하나로 서버가 전환했음을 의미.

---

### 100 Continue와 Expect 헤더

#### 클라이언트 측

- 엔터티 본문을 보내기 전에 100 Continue 응답을 기다리려면:  
  `Expect: 100-continue` 헤더를 포함해야 한다.
- 엔터티를 보낼 계획이 없다면 이 헤더를 쓰면 안 된다 → 서버 혼란 가능.
- 목적: 큰 엔터티를 서버가 처리할 수 있는지 확인 후 전송(최적화).
- 주의사항:
  - 오래된 구현 때문에 혼란이 있었음.
  - 클라이언트는 100 Continue 응답을 무기한 기다리면 안 된다.
  - 타임아웃 후 엔터티를 그냥 전송해야 한다.
  - 예상치 못한 100 Continue 응답에도 대비해야 한다.

#### 서버 측

- `Expect: 100-continue` 요청을 받으면:
  - `100 Continue` 또는 적절한 에러 코드로 응답.
  - 클라이언트가 의도하지 않았는데 100 Continue를 보내서는 안 된다.
- 이미 요청 본문의 일부/전체를 받은 경우:
  - `100 Continue`를 보낼 필요 없음 → 클라이언트는 이미 계속 전송 중.
- 요청을 끝까지 읽은 후에는 반드시 최종 응답을 보내야 한다.
- 요청을 끝내기로 결정(에러 등)했을 때:
  - 연결을 바로 닫지 말고, 응답을 정상적으로 보내야 한다.

#### 프락시 측

- 프락시는 `Expect: 100-continue` 헤더가 담긴 요청을 처리할 때 주의가 필요하다.

- 다음 홉 서버가 HTTP/1.1을 지원하거나 버전을 알 수 없는 경우:  
  → `Expect: 100-continue` 헤더를 그대로 전달한다.

- 다음 홉 서버가 HTTP/1.1 이전 버전임을 알고 있다면:  
  → `417 Expectation Failed` 에러로 응답해야 한다.

- 프락시가 HTTP/1.0 이하 클라이언트를 대신해서 `Expect: 100-continue`를 붙였을 경우:  
  → 클라이언트에게 `100 Continue` 응답을 전달해서는 안 된다. (클라이언트가 처리 불가)

- 프락시가 각 서버의 HTTP 버전 및 동작을 기억해 두면,  
  → `100-continue` 요청을 더 효율적으로 처리할 수 있다.

---

### 200–299: 성공 상태 코드

클라이언트 요청이 정상적으로 처리되었음을 나타낸다. 요청 유형에 따라 세부 코드가 다르다.

#### 주요 코드

- **200 OK**  
  요청 성공. 엔터티 본문에 요청한 리소스가 포함됨.

- **201 Created**  
  요청에 따라 서버에서 새 리소스가 생성됨.

  - `Location` 헤더에 생성된 리소스의 URL 제공
  - 본문에 참조 가능한 URL 포함

- **202 Accepted**  
  요청이 수락되었으나 아직 처리되지 않음.

  - 처리 완료 여부는 보장하지 않음
  - 본문에 상태/예상 완료 시각/확인 경로를 포함 가능

- **203 Non-Authoritative Information**  
  엔터티 헤더 정보가 원 서버가 아닌 사본에서 옴.

  - 캐시 등 중개자가 검증하지 않고 제공한 경우 발생
  - 반드시 필요한 코드는 아님 (선택적)

- **204 No Content**  
  응답에 본문이 없음.

  - 상태줄과 헤더만 포함
  - 예: 브라우저에서 폼 제출 후 페이지 새로고침 없이 갱신

- **205 Reset Content**  
  클라이언트(브라우저)에게 입력 폼을 초기화하라고 지시.

- **206 Partial Content**  
  범위 요청(range request)이 성공했음을 의미.
  - `Content-Range`, `Date` 헤더 필수
  - `ETag` 또는 `Content-Location` 중 하나도 반드시 포함

---

### 300–399: 리다이렉션 상태 코드

- 클라이언트가 요청한 리소스를 **다른 위치**에서 찾거나, 로컬 사본이 최신인지 확인할 때 사용.
- 응답에 `Location` 헤더가 포함되면, 브라우저는 자동으로 새 위치로 이동할 수 있다.
- 조건부 요청(예: `If-Modified-Since`)과 함께 사용하면, 리소스 변경 여부만 확인 가능.

#### 주요 코드

- **300 Multiple Choices**  
  여러 리소스를 가리킬 수 있는 URL → 목록 반환. (예: 다국어 문서)

- **301 Moved Permanently**  
  리소스가 영구적으로 옮겨짐. `Location` 헤더에 새 URL 제공.

- **302 Found**  
  임시 리다이렉트. 이후 요청에서는 원래 URL을 사용해야 한다.

- **303 See Other**  
  리소스를 다른 URL에서 가져오라고 지시. 주로 **POST 요청 응답**에 사용.

- **304 Not Modified**  
  리소스가 수정되지 않음. → 본문 없이 응답.

- **305 Use Proxy**  
  리소스 접근 시 특정 프락시를 반드시 거쳐야 함. (보안/호환성 문제로 잘 쓰이지 않음)

- **306**  
  현재 사용되지 않음.

- **307 Temporary Redirect**  
  302와 유사하지만, **요청 메서드를 바꾸지 않고** 그대로 리다이렉트해야 함.  
  (HTTP/1.1에서 POST 요청 리다이렉트 혼란을 해결하기 위해 도입)

## 헤더

- 헤더와 메서드는 함께 동작하며, 클라이언트·서버가 무엇을 해야 하는지 결정한다.
- 헤더는 크게 다섯 가지로 분류된다.

### 1. 일반 헤더 (General Headers)

- 클라이언트/서버 모두 사용 가능.
- 메시지 전체에 적용되는 일반 목적 정보.
- 예:  
  `Date: Tue, 3 Oct 1974 02:16:00 GMT` (메시지 생성 시각)

### 2. 요청 헤더 (Request Headers)

- 요청 메시지 전용.
- 클라이언트가 원하는 데이터 형식 등 부가 정보 제공.
- 예:  
  `Accept: */*` (모든 미디어 타입 수락)

### 3. 응답 헤더 (Response Headers)

- 응답 메시지 전용.
- 서버에 대한 정보 제공.
- 예:  
  `Server: Tiki-Hut/1.0` (서버 종류/버전)

### 4. 엔터티 헤더 (Entity Headers)

- 본문 데이터에 대한 정보.
- 예:  
  `Content-Type: text/html; charset=iso-latin-1` (본문이 HTML 문서이며 iso-latin-1 문자셋 사용)

### 5. 확장 헤더 (Extension Headers)

- 비표준, 애플리케이션 개발자가 정의한 헤더.

---

### 일반 헤더

메시지 종류(요청/응답)에 상관없이 공통적으로 쓰이는 기본 정보 헤더.

- **Connection** : 요청/응답 연결에 대한 옵션 지정
- **Date** : 메시지 생성 시각
- **MIME-Version** : 사용된 MIME 버전 명시
- **Trailer** : chunked transfer-encoding 끝에 올 헤더들의 목록
- **Transfer-Encoding** : 안전한 전송을 위해 적용된 인코딩 방식
- **Upgrade** : 업그레이드하고자 하는 프로토콜이나 버전
- **Via** : 메시지가 거쳐 온 중개자(프락시, 게이트웨이) 정보

---

#### 일반 캐시 헤더

캐싱 동작을 제어하기 위한 헤더.

- **Cache-Control** : 캐시 지시자 전달 (최신 HTTP에서 주로 사용)
- **Pragma** : 지시자 전달의 또 다른 방법 (캐시에 국한되지 않음, 주로 하위 호환 목적)
