# HTTP 메시지

## HTTP 메시지의 흐름

### 1. HTTP 메시지란?

- HTTP 메시지는 **HTTP 애플리케이션 간에 주고받는 데이터 블록**이다.
- 메시지는 **텍스트 기반의 메타 정보(헤더)**로 시작하고, 그 뒤에 **선택적으로 데이터(본문)**가 따라온다.
- 이 메시지는 **클라이언트, 서버, 프락시** 사이를 오가며 전달된다.

---

### 2. 메시지의 방향 개념

- 메시지의 이동 방향을 표현하는 주요 용어:
  - **인바운드 (Inbound)**: 메시지가 **원 서버(Origin Server)**로 향하는 방향
  - **아웃바운드 (Outbound)**: 원 서버에서 처리가 끝난 메시지가 다시 **사용자 에이전트(브라우저 등)**로 돌아오는 방향
  - **업스트림 (Upstream)**: 메시지를 보내는 쪽
  - **다운스트림 (Downstream)**: 메시지를 받는 쪽

---

### 3. 다운스트림으로 흐르는 메시지

- HTTP 메시지는 항상 **다운스트림**으로 흐른다.
- 요청/응답 여부와 관계없이 메시지의 수신자는 항상 발신자의 다운스트림이다.
- 예시:
  - 요청: 클라이언트 → 프락시1 → 프락시2 → 프락시3 → 원 서버
  - 응답: 원 서버 → 프락시3 → 프락시2 → 프락시1 → 클라이언트
- 따라서 같은 대상이 **요청 시 업스트림이자, 응답 시 다운스트림**이 될 수 있다.

---

## HTTP 메시지의 구성 요소

### 1. 메시지란?

- HTTP 메시지는 **데이터의 구조화된 블록**이다.
- 각 메시지는 **클라이언트의 요청** 또는 **서버의 응답** 중 하나를 담는다.
- 메시지는 크게 세 부분으로 나뉜다:
  1. **시작줄 (Start Line)** → 메시지의 성격 설명
  2. **헤더 블록 (Header Block)** → 속성 정보 전달
  3. **본문 (Body)** → 실제 데이터(없을 수도 있음)

---

### 2. 시작줄 (Start Line)

- 메시지가 **요청인지 응답인지** 알려주는 부분.
- 예:
  - 요청 메시지라면: `GET /index.html HTTP/1.1`
  - 응답 메시지라면: `HTTP/1.1 200 OK`

---

### 3. 헤더 블록 (Headers)

- 메시지나 본문에 대한 **부가 정보**를 제공한다.
- 줄 단위로 작성된 **아스키 문자열**이다.
- 각 줄은 `CRLF`(Carriage Return + Line Feed, `\r\n`)로 끝난다.
  - **CRLF**: 캐리지 리턴(ASCII 13) + 개행 문자(ASCII 10) → 전통적인 줄바꿈
  - 견고한 애플리케이션이라면 CRLF뿐만 아니라 단순 개행(`\n`)도 처리할 수 있어야 한다.
- 오래된 구현체 중 일부는 CR 또는 LF만 보내는 경우도 있다.

주요 헤더 예시:

- `Content-Type`: 본문 데이터의 타입 (예: `text/html`, `image/png`)
- `Content-Length`: 본문 데이터의 크기 (바이트 단위)

---

### 4. 본문 (Body)

- 선택적으로 포함되는 **실제 데이터** 덩어리.
- 없을 수도 있음.
- 텍스트나 이진 데이터를 모두 담을 수 있다.
- 헤더가 본문을 설명해준다.
  - 예: `Content-Type`, `Content-Length`

---

## HTTP 메시지 문법

### 1. 요청 메시지와 응답 메시지

- 모든 HTTP 메시지는 **요청 메시지** 또는 **응답 메시지**로 분류된다.
- **요청 메시지**: 클라이언트가 서버에 동작을 요구한다.
- **응답 메시지**: 서버가 요청의 결과를 클라이언트에 돌려준다.
- 요청과 응답은 기본 구조가 같지만, **시작줄**만 다르다.

---

### 2. 요청 메시지 형식

<메서드> <요청 URL> <버전>  
<헤더>

<엔터티 본문>

---

### 3. 응답 메시지 형식

<버전> <상태 코드> <사유 구절>  
<헤더>

<엔터티 본문>

---

### 4. 각 부분 설명

#### 메서드 (Method)

- 클라이언트가 서버에 원하는 동작.
- 예: `GET`, `HEAD`, `POST`

#### 요청 URL (Request URL)

- 요청 대상 리소스를 가리킨다.
- **완전한 URL** 또는 **경로 구성요소**로 표현 가능.
- 서버는 URL에 호스트/포트가 생략되면 자기 자신을 가리킨다고 간주한다.

#### 버전 (HTTP Version)

- 메시지에서 사용되는 HTTP 버전.
- 형식: `HTTP/<메이저>.<마이너>` (정수로 표현)

#### 상태 코드 (Status Code)

- 요청 처리 결과를 나타내는 **세 자리 숫자**.
- 첫 번째 자릿수가 결과의 대분류를 의미한다.
  - 예: 성공, 에러 등

#### 사유 구절 (Reason Phrase)

- 상태 코드의 의미를 사람이 읽을 수 있도록 짧게 설명한 문구.
- 상태 코드 뒤에 위치하며 줄바꿈(CRLF)까지 포함된다.
- 기계적 의미는 **숫자 코드**로만 결정된다.
  - 예:
    - `HTTP/1.0 200 OK`
    - `HTTP/1.0 200 NOT OK`  
      → 서로 다른 사유 구절이지만 동일하게 성공(200)으로 처리됨.

#### 헤더들 (Headers)

- 구조: `이름: 값 CRLF`
- 0개 이상 존재 가능.
- 헤더 목록은 반드시 **빈 줄(CRLF)**로 끝나며, 이것이 **본문 시작**을 알린다.
- 특정 HTTP 버전(예: HTTP/1.1)은 특정 헤더를 반드시 포함해야 한다.

#### 엔터티 본문 (Entity Body)

- 선택적으로 포함되는 **데이터 블록**.
- 모든 메시지가 본문을 가지는 것은 아니다.
- 메시지가 본문이 없더라도 헤더 집합은 항상 **빈 줄(CRLF)**로 끝나야 한다.

---

### 5. 주의할 점

- 실제 구현체 중에는 규약을 지키지 않고 마지막 CRLF를 빠뜨리는 경우가 있다.
- 클라이언트와 서버는 **마지막 CRLF가 없는 메시지**도 수용할 수 있도록 설계되어야 한다.

---

### 시작줄

- 모든 HTTP 메시지는 **시작줄(Start Line)**로 시작한다.
- **요청 메시지**의 시작줄 → 무엇을 해야 하는지 설명한다.
- **응답 메시지**의 시작줄 → 무슨 일이 일어났는지 설명한다.

---

#### 요청줄 (Request Line)

- 서버에 리소스에 대한 동작을 요청한다.
- 포함 요소:
  - **메서드(Method)**: 수행할 동작 (예: `GET`, `POST`)
  - **요청 URL(Request URL)**: 동작의 대상이 되는 리소스
  - **HTTP 버전(HTTP Version)**: 클라이언트가 사용하는 HTTP 버전
- 각 필드는 **공백으로 구분**된다.
- `HTTP/1.0` 이전에는 요청줄에 HTTP 버전이 없어도 되었다.

---

#### 응답줄 (Status Line)

- 클라이언트에게 **처리 결과**를 알려준다.
- 포함 요소:
  - **HTTP 버전(HTTP Version)**: 응답에 사용된 HTTP 버전
  - **상태 코드(Status Code)**: 요청 결과를 나타내는 숫자 (예: 200, 404)
  - **사유 구절(Reason Phrase)**: 상태 코드에 대한 짧은 설명 텍스트 (예: OK, Not Found)
- 각 필드는 **공백으로 구분**된다.
- `HTTP/1.0` 이전에는 응답줄이 없어도 되었다.
