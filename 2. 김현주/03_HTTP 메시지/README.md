# HTTP 헤더의 종류와 역할

HTTP헤더는 클라이언트와 서버가 서로 통신할 때 사용하는 부가적인 정보입니다.
요청(Request)과 응답(Response)메시지에 포함되며, 크게 몇 가지 종류로 나눌 수 있습니다.

1. 일반 헤더(General Headers)
   요청과 응답 메시지 모두에 적용되는 기본적인 헤더입니다. 메시지의 전체적인 속성을 나타냅니다. 예를 들어 Data헤더는 메시지가 생성된 날짜와 시간을 알려줍니다.
   예)

   - Date: 메시지가 생성된 시간
   - Cache-Control: 캐싱 정책 정의
   - Pragma: 이전 버전과 호환되는 캐시 지시자

2. 요청 헤더(Request Headers)
   클라이언트가 서버로 보내는 요청에만 사용되는 헤더입니다. 클라이언트가 선호하는 언어, 데이터 타입 등 서버가 더 나은 응답을 제공할 수 있도록 돕는 정보들이 담겨 있습니다.

- Host: 요청하는 서버의 호스트 이름과 포트 번호를 지정합니다.
- Referer: 현재 요처이 발생한 이전 페이지 URL
- User-Agent: 클라이언트 애플리케이션의 정보(브라우저 종류, OS 등)를 나타냅니다.
- Accept, Accept-Language, Accept-Encoding: 클라이언트가 수용 가능한 데이터 형식 지정
- 조건부 요청 관련: If-Modified-Since, If-None-Match

3. 응답 헤더(Response Headers)
   서버가 클라이언트에게 보내는 응답에만 사용되는 헤더입니다. 서버에 대한 정보나 응답 메시지의 속성을 담고 있습니다.

- Server: 요청을 처리한 웹 서버 소프트웨어의 정보를 알려줍니다.
- Age: 응답이 캐시된 이후로 얼마나 시간이 지났는지 초 단위로 나타냅니다.
- Retry-After: 언제 다시 시도해야 하는지
- Set-Cookie: 클라이언트에 쿠키 저장

4. 엔터티 헤더(Entity Headers)
   요청과 응답 메시지 모두에 포함될 수 있으며, 메시지 본문(entity body)에 대한 정보를 제공합니다.

- Content-Type: 본문에 담긴 데이터의 종류(예: text/html, image/jpeg)를 알려줍니다.
- Content-Length: 본문의 길이를 바이트 단위로 나타냅니다.
- Content-Encoding: 본문에 적용된 압축 방식(예: gzip)을 명시합니다.
- Content-Language: 사용 언어
- Content-Location: 실제 리소스 위치
- ETag, Expires, Last-Modified: 캐시 관련 정보

5. 엔터티 캐싱 헤더 (Entity Caching Headers)

- 캐시의 유효성을 관리하는 데 사용됩니다. **ETag**와 **Last-Modified**는 리소스가 변경되었는지 확인하여 불필요한 재전송을 막고 캐시를 효율적으로 사용하게 합니다.

- Cache-Control: 캐시의 동작 방식을 세밀하게 제어합니다.
- Last-Modified: 리소스가 마지막으로 수정된 날짜와 시간을 나타냅니다.
- ETag: 리소스의 특정 버전을 식별하는 태그를 제공합니다.

6. 보안 헤더(Security Headers)
   인증 및 보안과 관련된 정보를 다룹니다.

- Authorization: 클라이언트가 서버에 자신을 인증하기 위해 사용합니다.
- Cookie: 클라이언트 상태 유지에 사용
- Cookie2: 쿠키 버전 알림
- Set-Cookie: 서버가 클라이언트에 쿠키를 사용할 때 사용합니다.

7. 조건부 요청 헤더 (Conditional Request Headers)

- If- 접두사로 시작하는 헤더들로, **If-Modified-Since**나 **If-None-Match**처럼 특정 조건을 만족할 때만 요청을 처리하도록 합니다. 이는 서버와 네트워크의 부하를 줄이는 데 유용합니다.

8. 응답 보안 헤더
   서버에서 인증 요구 시 사용

- Proxy-Authenticate: 프록시 인증 요구
- WWW-Authenticate: 서버 인증 요구

# HTTP 메시지 구조와 메서드

1. HTTP 메시지 구조

- 요청 메시지: 클라이언트 → 서버(무엇을 원하는지 전달)
- 응답 메시지: 서버 → 클라이언트(요청에 대한 결과 전달)
- 메시지는 세 부분으로 구성됨
  1. 시작줄(메서드/상태 코드/버전)
  2. 헤더(부가 정보)
  3. 본문(데이터)

2. 메시지 흐름

- HTTP 메시지는 클라이언트 ↔ 서버 ↔ 프록시 사이를 흘러가는 데이터 블록.
- 방향
  - 인바운드(inbound): 서버로 향하는 요청.
  - 아웃바운드(outbound): 클라이언트로 돌아오는 응답.
  - 업스트림(upstream) / 다운스트림(downstream) 개념으로 설명 가능.

3. 메시지 구조(3부분)
   1. 시작줄

- 요청: <메서드> <요청 URL> <버전>
  예) GET /index.html HTTP/1.1
- 응답: <버전> <상태 코드> <사유 구절>
  예) HTTP/1.1 200 OK

  2.  헤더

- 키:값 형태.
- 요청/응답/엔터티에 대한 부가 정보 제공.
- CRLF(빈 줄)로 끝남.

  3. 본문(Entity Body)

  - 실제 데이터(HTML, 이미지, JSON 등).
  - 없을 수도 있음.

4. 상태 코드(Status Code)

- 세 자리 숫자, 범위별 의미
  - 1xx (정보): 요청 처리 중 추가 정보.
  - 2xx (성공): 요청 성공 (예: 200 OK).
  - 3xx (리다이렉션): 다른 위치로 이동 필요.
  - 4xx (클라이언트 오류): 요청 잘못됨 (예: 404 Not Found).
  - 5xx (서버 오류): 서버 처리 실패 (예: 500 Internal Server Error).

5.  주요 메서드(Method)
    | 메서드 | 설명 | 본문 포함 여부 |
    | :--------------- | :------------------------| :----------------------------- |
    | GET | 리소스 조회 | 없음 |
    | HEAD | 리소스 메타데이터만 조회, 상태줄과 헤더만 반환 | 없음 |
    | POST | 가능 | 데이터 전송(폼, 업로드 등) |있음 |
    | PUT | 지정한 URL에 데이터 저장 | 있음 |
    | DELETE | 리소스 삭제 | 없음 |
    | TRACE | 요청을 그대로 반환 (루프백 테스트) | 있음 |
    | OPTIONS | 대상 리소스에 대한 통신 가능 옵션(메서드)을 설명(주로 CORS에서 사용) | 없음 |

GET과 POST는 웹 통신에서 가장 기본적으로 사용되는 HTTP 메소드입니다. 이 둘은 웹 서버에 특정 작업을 요청할 때 사용되지만, 각각의 목적과 특성이 다릅니다.

# 안전한 메소드(Safe Methods)

서버의 상태를 변경하지 않는 메소드입니다. GET과 HEAD가 이에 해당하며, 서버에 어떤 부작용도 일으키지 않습니다.

# HEAD

GET과 유사하지만, 응답에서 본문 없이 헤더만 받습니다. 이를 통해 리소스가 변경되었는지, 존재 여부 등을 효율적으로 확인할 수 있습니다.

# GET 메소드

GET과 POST는 웹 통신에서 가장 기본적으로 사용되는 HTTP 메소드입니다. 이 둘은 웹 서버에 특정 작업을 요청할 때 사용되지만, 각각의 목적과 특성이 다릅니다.

GET 메소드
GET은 서버로부터 데이터를 가져오는(Retrieve) 데 사용됩니다. 예를 들어, 웹사이트에 접속하거나 검색을 할 때 주로 이 메소드가 사용됩니다.

- 안정성(Idempotent): 여러 번 반복해서 요청해도 서버의 데이터가 변경되지 않습니다. 같은 요청을 100번 보내도 결과는 동일합니다.
- 데이터 노출: 데이터는 URL의 쿼리 스트링(Query String)에 포함되어 전송됩니다. 이 때문에 데이터가 외부에 노출되어 보안에 취약할 수 있고, 전송할 수 있는 데이터 양에도 제한이 있습니다.
- 캐싱 가능: 브라우저나 프록시 서버에 의해 캐싱될 수 있어 속도가 빠르지만, 민감한 정보를 다룰 때는 사용하지 않아야 합니다.

# POST 메소드

POST는 서버에 데이터를 제출하거나(Submit), 새로운 리소스를 **생성(Create)**할 때 사용됩니다. 예를 들어, 회원가입 양식을 제출하거나 게시글을 작성할 때 사용됩니다.

- 비안전성 (Non-Idempotent): 요청을 반복할 때마다 서버에 새로운 데이터가 생성되거나 기존 데이터가 변경될 수 있습니다.
- 데이터 비노출: 데이터는 HTTP 요청의 **본문(Body)**에 담겨 전송됩니다. URL에 데이터가 보이지 않아 GET보다 보안에 강하고, 전송할 수 있는 데이터 양에 제한이 없습니다.
- 캐싱 불가: 서버에 새로운 리소스를 생성하는 등의 부작용이 있을 수 있어 캐싱되지 않습니다.

GET은 "책을 읽는 것"과 같습니다. 어떤 책을 읽든 책의 내용은 변하지 않습니다.
POST는 "책에 글을 쓰는 것"과 같습니다. 글을 쓸 때마다 책의 내용이 바뀌고 새로운 정보가 추가됩니다.

| 특징             | GET                | POST                           |
| :--------------- | :----------------- | :----------------------------- |
| 목적             | 데이터 조회        | 데이터 제출/생성/변경          |
| 데이터 전송 위치 | URL의 쿼리 스트링  | HTTP 요청 본문                 |
| 캐싱             | 가능               | 불가능                         |
| 데이터 노출      | 노출됨 (보안 취약) | 노출되지 않음                  |
| 전송량 제한      | 제한적 (URL 길이)  | 거의 무제한                    |
| 안전성           | 안전 (Idempotent)  | 안전하지 않음 (Non-idempotent) |
