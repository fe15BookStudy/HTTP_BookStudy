# 01 HTTP - 웹의 기초

### 3장 HTTP 메세지

#### 3.1 메세지의 흐름

- HTTP 메세지는 HTTP 애플리케이션 간에 주고받은 데이터의 블록들.

  이 메세지는 클라이언트 , 서버 , 프락시 사이를 흐르는데, `인바운드` , `아웃바운드`, `업스트림`, `다운스트림` 의 방향을 가짐.

#### 3.1.1 메세지는 원 서버 방향을 인바운드로 하여 송신

- 메세지가 원 서버로 향하는 것은 `인바운드`, 모든 처리가 끝난 후 메세지가 사용자 에이전트로 돌아오는 것은 `아웃바운드`.

#### 3.1.2 다운스트림으로 흐르는 메세지

- HTTP 메세지의 모든 메세지는 다운스트림으로 흐른다. 메세지의 발송자는 수신자의 업스트림이다.

---

### 3.2 메세지의 각 부분

#### 3.2.1 메세지 문법

- 모든 메세지는 요청 메세지나 응답 메세지로 분류 된다.

요청 메세지의 형식은 다음과 같다.

<메서드> <요청url><버전>

<헤더>

<엔터티 본문>

응답 메세지의 형식은 다음과 같다.

<버전> <상태코드><사유 구절>

<헤더>

<엔터티 본문>

---

각 부분에 대한 설명은 다음과 같다.

1.  메서드

        - 클라이언트 측에서 서버가 리소스에 대해 수행해주길 바라는 동작

    'GET' , 'HEAD' , 'POST' 와 같이 한 단어로 되어 있다.

2.  요청 URL

    - 요청 대상이 되는 리소스를 지칭하는 완전한 URL 혹은 URL의 경로 구성요소다.

3.  버전

    - 이 메세지에서 사용 중인 HTTP의 버전이다. 형식은 다음과 같다.

      HTTP/<메이저>.<마이너>

    메이저와 마이너는 모두 정수다.

4.  상태 코드

    - 요청 중에 무엇이 일어났는지 설명하는 세 자리 숫자다. 각 코드의 첫 번째 자릿수는 상태의 일반적인 분류('성공', '에러'등)를 나타낸다.

5.  사유 구절

    - 숫자로 된 상태 코드의 의미를 사람이 이해할 수 있게 설명해주는 짧은 문구.

6.  헤더들

    - 이름, 콜론(:), 선택적인 공백, 값, CRLF가 순서대로 나타나는 0개 이상의 헤더들. 이 헤더의 목록은 빈 줄(CRLF)로 끝나 헤더 목록의 끝과 엔터티 본문의 시작을 표시한다.

7.  엔터티 본문

    - 엔터티 본문은 임의의 데이터 블록을 포함한다. 모든 메세지가 엔터티 본문을 갖는 것은 아니므로, 때때로 메세지는 그냥 CRLF 으로 끝나게 된다.

---

#### 3.2.2 시작줄

모든 HTTP 메세지는 시작줄로 시작한다. 요청 메세지의 시작줄은 무엇을 해야하는지를, 응답 메세지의 시작줄은 무슨 일이 일어났는지를 말해준다.

1. 요청줄

   - 요청 메세지는 서버에게 리소스에 대해 무언가를 해달라고 부탁한다. 요청 메세지의 시작줄, 혹은 요청줄에는 서버에서 어떤 동작이 일어나야 하는지 설명해주는 메서드와 그 동작에 대한 대상을 지칭하는 요청 URL이 들어있다.

2. 응답줄

   - 응답 메세지는 수행 결과에 대한 상태 정보와 결과 데이터를 클라이언트에게 돌려준다. 응답 메세지의 시작줄 혹은 응답줄에는 응답 메세지에서 쓰인 HTTP의 버전, 숫자로 된 상태 코드 , 수행 상태에 대해 설명해주는 텍스트로 된 사유 구절이 들어 있다.

3. 메서드

   - 요청의 시작줄은 메서드로 시작하며, 서버에게 무엇을 해야 하는지 말해준다. 예를 들어, 'GET/specials/saw-blade.gif HTTP/1.0' 이라는 줄에서 메서드는 GET이다.

4. 상태 코드

   - 메서드가 서버에게 무엇을 해야 하는지 말해주는 것처럼, 상태 코드는 클라이언트에게 무엇이 일어났는지 말해준다. 상태 코드는 응답의 시작줄에 위치한다. 예를 들어 'HTTP/1.0 200 OK' 라는 줄에서 상태 코드는 200이다.

5. 사유 구절

   - 사유 구절은 응답 시작줄의 마지막 구성요소이다. 이것은 상태 코드에 대한 글로 된 설명을 제공한다. 사유 구절은 코드와 일대일로 대응된다.

6. 버전 번호

   - 버전 번호는 HTTP/x.y 형식으로 요청과 응답 메세지 양쪽 모두에 기술된다. 이것은 HTTP 애플리케이션들이 자신이 따르는 프로토콜의 버전을 상대방에게 말해주기 위한 수단이 된다.

---

#### 3.2.2 헤더

시작줄 다음에는 0개, 1개 혹은 여러 개의 HTTP 헤더가 온다.

HTTP 헤더 필드는 요청과 응답 메세지에 추가 정보를 더한다. 그들은 기본적으로 이름/값 쌍의 목록이다.

HTTP 헤더는 다음과 같이 분류된다.

- 일반 헤더 : 요청과 응답 양쪽에 모두 나타날 수 있음

- 요청 헤더 : 요청에 대한 부가 정보를 제공

- 응답 헤더 : 응답에 대한 부가 정보를 제공

- Entity 헤더 : 본문 크기와 콘텐츠, 혹은 리소스 그 자체를 서술

- 확장 헤더 : 명세에 정의되지 않은 새로운 헤더

<br>

### 3.3 메서드

<br>

#### 3.3.2 GET

GET은 가장 흔히 쓰이는 메서드다. 주로 서버에게 리소스를 달라고 요청하기 위해서 쓰인다.

---

#### 3.3.3 HEAD

HEAD 메서드는 정확히 GET 처럼 행동하지만, 서버는 응답으로 헤더만을 돌려준다. 엔터티 본문은 결코 반환되지 않는다.

HEAD를 사용하면,

- 리소스를 가져오지 않고도 그에 대해 무엇인가를 알아낼 수 있다.

- 응답의 상태 코드를 통해, 개체가 존재하는지 확인할 수 있다.

- 헤더를 확인하여 리소스가 변경되었는지 검사 할 수 있다.

서버 개발자들은 반드시 반환되는 헤더가 GET으로 얻는 것과 정확히 일치함을 보장해야 한다.

---

#### 3.3.4 PUT

GET 메서드가 서버로부터 문서를 읽어 들이는데 반해 PUT 메서드는 서버에 문서를 쓴다.

PUT 메서드의 의미는, 서버가 요청의 본문을 가지고 요청 URL 의 이름대로 새 문서를 만들거나, 이미 URL 이 존재한다면 본문을 사용해서 교체하는 것이다.

---

#### 3.3. 5 POST

POST 메서드는 서버에 입력 데이터를 전송하기 위해 설계되었다. 실제로, HTML 폼을 지원하기 위해 흔히 사용된다. 채워진 폼에 담긴 데이터는 서버로 전송되며, 서버는 이를 모아서 필요로 하는 곳에 보낸다.

---

#### 3.3.6 TRACE

클라이언트가 어떤 요청을 할 때, 그 요청은 방화벽, 프락시, 게이트웨이 등의 애플리케이션을 통과 할 수 있다.

이들에게는 원래의 HTTP 요청을 수정할 수 있는 기회가 있다. TRACE 메서드는 클라이언트에게 자신의 요청이 서버에 도달했을 때 어떻게 보이게 되는지 알려준다.

TRACE 메서드는 주로 진단을 위해 사용된다.

---

#### 3.3.7 OPTIONS

OPTIONS 메서드는 웹 서버에게 여러 가지 종류의 지원 범위에 대해 물어본다. 서버에게 특정 리소스에 대해 어떤 메서드가 지원되는지 물어볼 수 있다.

---

#### 3.3.8 DELETE

DELETE 메서드는 서버에게 요청 URL로 지정한 리소스를 삭제할 것을 요청한다.

---

#### 3.3.9 확장 메서드

HTTP는 필요에 따라 확장해도 문제가 없도록 설계되어 있으므로, 새로 기능을 추가해도 과거에 구현된 소프트웨어들의 오동작을 유발하지 않는다. 확장 메서드는 HTTP/1.1 명세에 정의되지 않은 메서드다.

---

### 3.4 상태 코드

HTTP 상태 코드는 클라이언트가 서버에 요청을 보냈을 때 그 요청의 처리 결과를 나타내는 숫자 코드다. 이는 크게 5가지 범주로 나눌 수 있다.

---

#### 3.4.1 1xx : 정보성 상태 코드

요청은 잘 수신되었고, 클라이언트는 계속 요청을 진행해도 된다는 의미를 가진다.

1. 100 Continue: 클라이언트가 요청 본문을 보내도 된다는 신호. 주로 Expect: 100-continue 헤더와 함께 사용된다.

2. 101 Switching Protocols: 서버가 프로토콜 전환을 승인했음을 의미.

<br>

---

#### 3.4.2 2xx : (성공 상태 코드)

클라이언트 요청이 성공적으로 처리됨을 의미한다.

1. 200 OK: 요청 성공. 일반적인 성공 응답.

2. 201 Created: 새로운 리소스가 생성됨. Location 헤더에 새 리소스의 URL 포함.

3. 202 Accepted: 요청이 수락되었으나 아직 처리 완료는 아님.

4. 204 No Content: 성공했지만 반환할 본문 없음.

5. 206 Partial Content: 리소스의 일부만 반환. 주로 범위 요청(range request)에 사용됨.

<br>

---

#### 3.4.3 3xx : (리다이렉션 상태 코드)

클라이언트가 요청을 완료하려면 추가 동작(다른 URL로 이동 등)이 필요함을 의미한다.

1. 300 Multiple Choices: 여러 리소스 중 선택 가능.

2. 301 Moved Permanently: 리소스가 영구적으로 이동됨. 새 URL은 Location 헤더에 제공됨.

3. 302 Found: 임시적으로 다른 URL 사용.

4. 303 See Other: 다른 URL을 GET 방식으로 요청해야 함.

5. 304 Not Modified: 리소스가 수정되지 않았으므로 캐시된 버전 사용 가능.

6. 307 Temporary Redirect: 요청 메서드를 그대로 유지한 채 임시 리다이렉트.

<br>

---

#### 3.4.4. 4xx : (클라이언트 에러 상태 코드)

클라이언트의 잘못된 요청으로 인해 서버가 요청을 처리할 수 없다.

1. 400 Bad Request: 잘못된 요청.

2. 401 Unauthorized: 인증 필요.

3. 403 Forbidden: 권한 없음. 접근 금지.

4. 404 Not Found: 리소스를 찾을 수 없음.

5. 405 Method Not Allowed: 해당 리소스에서 허용되지 않은 메서드 사용.

6. 408 Request Timeout: 요청 시간이 초과됨.

7. 409 Conflict: 요청이 서버 상태와 충돌.

8. 413 Request Entity Too Large: 요청 본문이 너무 큼.

9. 414 Request URI Too Long: 요청 URI가 너무 김.

10. 415 Unsupported Media Type: 지원되지 않는 미디어 타입.

11. 417 Expectation Failed: Expect 헤더 조건을 충족하지 못함.

<br>

---

#### 3.4.5 5xx : (서버 에러 상태 코드)

서버 자체에서 문제가 발생해 요청을 처리할 수 없다.

1. 500 Internal Server Error: 일반적인 서버 내부 오류.

2. 501 Not Implemented: 서버가 해당 기능을 지원하지 않음.

3. 502 Bad Gateway: 게이트웨이/프록시 서버가 잘못된 응답을 받음.

4. 503 Service Unavailable: 서버 과부하/점검으로 서비스 불가.

5. 504 Gateway Timeout: 게이트웨이/프록시 서버가 응답을 제때 받지 못함.

6. 505 HTTP Version Not Supported: 지원되지 않는 HTTP 버전 사용.

<br>

---

### 3.5 헤더

#### 3.5.1 요청 헤더(Request Header)

클라이언트가 서버에 요청을 보낼 때 추가하는 정보이다.

클라이언트의 종류, 선호하는 언어, 요청하는 문서의 캐시 상태 등 다양한 정보를 담고 있다.

예를 들면 User-Agent는 클라이언트의 애플리케이션 정보를 나타내고 Accept-Language는 클라이언트가 선호하는 언어를 명시한다.

#### 3.5.2 응답 헤더(Response Header)

서버가 클라이언트의 요청에 응답할 때 보내는 정보이다.

응답을 보낸 서버의 종류, 메시지가 생성된 시간 등 추가적인 정보를 담고 있다.

예를 들어 Server는 응답을 보낸 웹 서버의 종류를 알려주고 Date는 메시지가 생성된 시각을 나타낸다.

#### 3.5.3 엔터티 헤더(Entity Header)

요청 및 응답 메시지의 본문(entity body)에 대한 정보를 담고 있다.

이 헤더는 콘텐츠의 종류, 길이, 압축 방식 등 본문 내용을 설명하는 역할을 한다.

예를 들면 Content-Type은 본문의 미디어 타입(예: text/html, image/jpeg)을 명시하고 Content-Length는 본문의 길이를 바이트 단위로 나타낸다.
